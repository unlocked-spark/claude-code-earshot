# Spike results, October 2026

Answers to the open questions in `specs/screen-reader-detection.md`, read from the mod API type declarations that Claude Code 2.1.295 writes (`claude-code.d.ts`, laid beside the mod as `.claude-plugin/types/claude-code/index.d.ts`) and from `claude plugin validate`. Items marked "manual" still need a session with a screen reader.

## Spike A: can a `prompt.submit` hook consume the submission?

Yes. A hook that returns `{ drop: reason }` without calling `next` stops the prompt from reaching the model; the reason is shown to the user. A drop returned after `next(e)` resolved fails the hook instead. The mod answers `y` and `n` this way while its question is pending and passes everything else on. Consent therefore stays a typed `y`/`n`, as the spec says; the commands remain as the fallback.

Still manual: how the drop reason is drawn and whether a screen reader reads it in a graphical session.

## Spike B: `$.audio.speak` on Windows and Linux

Not answerable from the types. The declaration says speech uses "the platform's own synthesizer (`say` on macOS)" and rejects, naming the cause, when there is no synthesizer. The mod catches that rejection, so a silent platform loses speech but keeps the transcript line and the native notification. Milestone M3 covers a SAPI or NVDA bridge through `$.process.run`.

Still manual: Windows 11 with NVDA (TC-002).

## Spike C: own version, plugin root, atomic writes

- `$.plugin.name` and `$.plugin.root` exist; there is no version field. The mod reads `${$.plugin.root}/.claude-plugin/plugin.json` through `$.fs.read` and falls back to `0.0.0`.
- `$.fs` offers `read`, `write`, `exists`, `stat`, `list` and `ancestors`. There is no rename, so the settings write is write, read back, compare; before the first write of a session the previous content is copied to `settings.json.a11y-backup`.
- `$.settings.read({ source: 'user' })` reads the user file as the engine parsed it, and `$.settings.read()` the merge over every source, so mode state needs no JSON parsing of our own. The file is still read as text for the write, through a strict `JSON.parse` that refuses comments and trailing commas (AC-013).
- `$.env.get` takes a string literal; the validator lists the names read (`CLAUDE_AX_SCREEN_READER`, `HOME`, `OS`, `USERPROFILE`).
- The module runs with no Node and no DOM. Platform comes from the `OS` variable (`Windows_NT`) and otherwise from `uname -s`.

## Loader constraints found on the way

- `$` may only be passed to functions declared at the top of the hooks module. Helpers inside the `register` closure, or a function parameter that receives `$`, make the module fail to load. The mod keeps its session facts in one module-level record and every helper top-level.
- Plugin names starting with `claude-`, `anthropic-` or `cc-plugin-` are reserved; the mod is `a11y-companion` while the repository stays `claude-code-a11y`.
- Command names allow letters, digits, `_` and `-` only, so the commands are `/a11y-on`, `/a11y-off` and `/a11y-status`, not the `/a11y:on` the spec first used.
- The terminal bell is not a call of its own. `$.ui.notify` writes to the user's `preferredNotifChannel`, which rings when that channel is `terminal_bell`.
- `claude plugin test .` runs `hooks/*.test.ts` with the `claude-code/testing` kit and does not descend into `node_modules`. Stubs beneath the mod answer each call's event with `{ value }`; `mock.env`, `mock.store` and `mock.clock` cover those nouns; the test answers `session.start` and `prompt.submit` at the bottom of the chain.
